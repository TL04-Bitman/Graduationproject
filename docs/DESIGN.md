# 设计文档（DESIGN）

> 面向对象：代码评审人、后续接手维护者。
> 本文回答三个问题：**为什么这样建模**、**算法怎么跑**、**效果如何量化**。

---

## 1. 需求与角色

| 角色 | 诉求 | 系统提供的功能 |
| --- | --- | --- |
| 教务（排课员） | 一个学期上百个教学班，要在有限的教室与时段里排出**无冲突**的课表；课程先修关系不能出错 | 一键排课、拓扑序与分层教学计划、循环依赖检测与演练、全校课表、教师工作量、教室使用率、排课审计 |
| 学生 | 选课前想知道「我能不能选这门课」，选课后想看到**一张能看懂的课表** | 登录、可选课程（标注不可选原因）、选课、退课、周课表网格、先修进度、历史成绩 |
| 教务（教学计划维护） | 维护课程先修关系时不希望把数据搞成环 | 新增/删除先修关系（写入前自动试算防环） |

**业务约束清单**（同时是验收标准）：

1. 课程先修关系必须构成 DAG；出现循环依赖时必须**自动报错并终止**，不允许产生半成品数据。
2. 排课结果中：同一教师同一时段不冲突、同一教室同一时段不冲突、同一教学班同一时段不重复；
   教室容量必须放得下预期人数；教师教学班数不超过工作量上限。
3. 学生选课必须校验：学籍状态、教学班状态、重复选课、先修通过、学分上限、容量、时间冲突。
4. 所有失败都必须给用户**可读的中文原因**，而不是一个错误码。

## 2. 领域模型

```
 semesters ──┐
             │ 1:N
 courses ◄───┼────────── course_prerequisites (DAG 的边: prereq → course)
    ▲        │
    │ 1:N    │
 teaching_classes ── N:1 ── teachers
    │   │            ── N:1 ── classrooms (通过 schedule_entries)
    │   │
    │   └── 1:N ── schedule_entries (一个教学班每周的固定上课时段)
    │
students ── N:M ── enrollments (选课/成绩, 同时承载"先修是否修过"的信息)
```

关键取舍：

- **教学班（teaching_classes）是排课与选课的最小单位**，而不是课程本身：
  同一门课可以开多个班（不同教师/容量），学生选的是班，排课排的也是班。
- **先修关系挂在课程上**（`course_prerequisites`），因为是培养方案层面的约束；
  但**先修是否满足是在学生层面判断的**（该生是否修过并及格）。
- **历史成绩复用 `enrollments`**：状态为 `completed` 且分数 ≥ 及格线，即视为"先修已通过"，
  无需为历史成绩再建一张表（这也是教务系统的常见做法）。

## 3. 先修关系为什么是 DAG

### 3.1 建模

- **顶点** = 课程（27 门）
- **有向边** = 先修关系，方向 `先修课 → 后续课`（例如 `CS101 → CS201`）

方向的选取有一个现实理由：**边的方向就是学习的先后顺序**。于是

- 拓扑序 = 一条合法的修读顺序（先修课一定排在后继课之前）；
- 排课时按拓扑序处理教学班 = **先修课优先占用稀缺资源**（好时段、机房），
  这直接对应教务处的实际做法（基础课优先保障）。

### 3.2 示例（本项目演示数据的关键链路）

```
CS101 程序设计基础 ──► CS201 数据结构与算法 ──► CS204 数据库原理 ──► CS305 数据库系统实现
        │                    │                       │
        │                    └──► CS301 算法设计与分析 ──► CS302 编译原理
        └──► CS202 计算机组成原理 ──► CS205 操作系统 ──► CS306 分布式系统 ──► CS311 云计算与大数据
MA101 高等数学(上) ──► MA102 / MA201 / MA202 / CS102，CS102 ──► CS201 / CS301 / CS309
```

最长先修链 5 层，共 27 顶点 / 33 边，`./build/scheduler topo` 可直接打印分层结果。

### 3.3 两道防线拦住"自环"

- 数据库层：`chk_prereq_no_selfloop CHECK (course_id <> prereq_course_id)`
  —— 自环（A 以自己为先修）必然成环，写入阶段直接拒绝。
- 应用层：长度 ≥ 2 的环由 Kahn 算法在拓扑排序时检出（见下节）。

## 4. Kahn 拓扑排序

### 4.1 算法与伪代码

```
入度 indegree[v] = |{先修课 of v}|
就绪队列 Q ← { v | indegree[v] == 0 }
order ← []
while Q 非空:
    v ← Q.pop()                     # 出队即确定顺序
    order.append(v)
    for s in 后继(v):
        indegree[s] -= 1
        if indegree[s] == 0: Q.push(s)
# 结束: 比较 len(order) 与 顶点总数
```

实现要点（`src/graph/dag.cpp`，约 60 行核心逻辑）：

1. **就绪队列用 `std::priority_queue`**，并按策略给出优先级键：
   - `Fifo`：按入队先后（最朴素的 Kahn，用于对照）；
   - `StableByKey`：按课程编号（输出可复现，便于测试与审计）；
   - `LevelThenKey`：按「先修层级 → 课程编号」，**生产环境默认**。
   只有入度为 0 的顶点才允许出队，因此任何策略下的输出都是合法拓扑序（有单元测试覆盖）。
2. **后继遍历前按课程编号排序**，保证同一批入度归零的顶点处理顺序确定 —— 相同输入永远得到相同输出。
3. **迭代实现**，不递归，5000 顶点深链不会爆栈（有测试验证）。
4. 复杂度 **O(V + E)**，空间 O(V + E)。

### 4.2 分层（教学计划）

`compute_levels()` 用一次「按入度推进的 BFS」计算最长路径层级：
层 0 = 无先修课，其余 = `max(先修课层级) + 1`。同层课程互不依赖，可安排在同一学年段。
这一信息既用于拓扑排序的优先级，也直接展示为「分层教学计划」。

## 5. 循环依赖检测机制（本项目的核心亮点）

### 5.1 判据

> **拓扑排序输出的序列长度 ≠ 课程总数 ⇒ 先修关系存在循环依赖。**

原因很直白：Kahn 算法每轮只能处理「入度为 0」的顶点。若图中有环，环上每个顶点都至少有一条
来自环内前驱的入边，**入度永远无法归零**，于是它们永远不会进入结果序列。

### 5.2 从"检测到"到"可定位"

只报「有环」对教务不够用，还需要指出**环在哪里**。因此：

1. 未出现在序列中的顶点集合 = 所有被阻塞的顶点（`pending`，含环上顶点与依赖环的下游顶点）；
2. 用**迭代式 DFS + 三色标记**在这些顶点中找出一个具体环路：
   沿着有向边走，遇到仍在当前搜索栈上的"灰色"顶点即发现回边，
   把搜索栈从该祖先到栈顶的一段截取出来，再补上祖先自身即可闭合（`find_cycle_path()`）。

输出形如：

```
判据: 拓扑序列长度 22 ≠ 课程总数 27
环路路径: CS101 → CS202 → CS205 → CS306 → CS311 → CS101
受阻课程(5 门): CS101, CS202, CS205, CS306, CS311
```

### 5.3 100% 准确率是怎么验证的

`tests/test_graph.cpp::cycle_detection_accuracy_on_random_graphs_is_100_percent`
随机生成 **500 张图**（顶点 4~14、约 30% 边密度、偶发自环，固定随机种子可复现），
对每张图用**两条互不相干的算法路线**判定是否存在环：

| 路线 | 方法 | 角色 |
| --- | --- | --- |
| 被测实现 | Kahn 拓扑排序 → 序列长度 ≠ 顶点总数？ | 待验证 |
| 基准真值 | Warshall 传递闭包 → 是否存在可达自身的顶点？ | 独立算法族，作为 ground truth |

断言：两者结论**逐个一致**（零误报、零漏报），即准确率 100%。同时还校验：

- 无环时：序列长度 = 顶点数，且**所有边都满足「先修在前」**（逐边验证拓扑序合法性）；
- 有环时：**环路真实存在**（相邻顶点间确实有边、首尾闭合）。

实测输出（`./build/scheduler_tests`）：

```
[随机对照] 图样本 500 个(有环 473 / 无环 27, 共 12463 条边):
           Kahn 判环与 Warshall 真值一致 500/500 => 准确率 100%
```

补充覆盖的固定用例：自环、二元环、三元环、两个不相交的环、长链绕回起点、
环与健康子图混合（校验"受阻顶点数 = 总顶点数 − 已排序顶点数"）。

### 5.4 三处防守，保证"不会写出带环的教学计划"

| 时机 | 位置 | 行为 |
| --- | --- | --- |
| 写入前 | `CurriculumService::add_prerequisite` | 把候选边加入内存 DAG 试算；一旦成环 → 抛 `CycleDetectedError`，**拒绝写库** |
| 排课前 | `SchedulingService::generate` 第 ② 步 | 拓扑校验失败 → **中止排课**，不删除、不写入任何排课记录，只落一条 `cycle_detected` 审计 |
| 演示/巡检 | `scheduler cycle-check`、界面「循环依赖检测/演练」 | 只报告不修改；演练会临时注入环并自动恢复现场 |

### 5.5 演练流程（可直接演示给评审人看）

```
① 直接写库注入错误边 CS311 → CS101（刻意绕过防环校验，用来验证检测机制本身）
② 检测: 序列长度 22 ≠ 27, 环路 CS101 → CS202 → CS205 → CS306 → CS311 → CS101
③ 排课: 立即中止, 排课记录条数不变(前后对比证明未写入脏数据)
④ 删除该边恢复现场, 重新检测通过
```

## 6. 排课算法（一键排课的完整业务流程）

### 6.1 流程时序

```
① 读取启用课程 + 先修关系 → 装配 DAG（顶点 = 课程，边 = 先修）
② Kahn 拓扑排序 + 环校验
        └─ 序列长度 ≠ 课程总数 → 记录审计(status=cycle_detected) → 抛异常, 流程结束
③ 载入资源与教学班: 教师 / 教室 / 节次 / 本学期教学班（并按拓扑序排列教学班队列）
④ 逐个教学班分配「时段 + 教室」（纯内存核心算法 run_placement）
        对教学班的每个课次（course.class_hours_per_week）:
          候选时段 = 全部时段 − 本班已占时段, 排序键 = (是否与已占用同日, 时段权重)
          候选教室 = 容量 ≥ 预期人数, 排序键 = (类型是否匹配, 容量浪费量, 教室编号)
          for 时段 in 候选时段:               # 先筛时段, 省掉大量教室试探
              if 教师在该时段忙: continue
              for 教室 in 候选教室:
                  if 教室在该时段忙: continue
                  → 命中, 记录方案(班级/课程/教师/教室/时段), 跳出
          若某课次找不到任何组合 → 该教学班整体判为"需人工处理", 不提交部分占用
⑤ 事务落库: 清空本学期旧结果 + 批量写入新结果 + 写入审计记录（同事务, 异常整体回滚）
⑥ 自检: 从库里读回结果, 独立校验教师/教室/班级三类冲突是否为 0
```

### 6.2 约束分层

| 类型 | 约束 | 实现位置 |
| --- | --- | --- |
| 硬约束 | 同一教师同一时段唯一 | `ConflictMatrix` + 数据库唯一索引 `uk_teacher_slot` |
| 硬约束 | 同一教室同一时段唯一 | `ConflictMatrix` + `uk_room_slot` |
| 硬约束 | 同一教学班时段不重复 | 候选时段剔除 + `uk_class_slot` |
| 硬约束 | 教室容量 ≥ 预期人数 | `rules::rank_classrooms` 过滤 |
| 硬约束 | 教师教学班数 ≤ `teachers.max_classes` | 排课主循环前置检查 |
| 软约束 | 上午优先（`time_slots.slot_weight`） | `rules::order_candidate_slots` |
| 软约束 | 同一门课不同课次不排在同一天 | 同上（同日惩罚项） |
| 软约束 | 实践类课程优先机房、大教室留给大班 | `rules::rank_classrooms` |

**设计取舍**：先判教师再判教室。教师冲突会让整个时段不可用，直接跳过该时段可以省下
「时段数 × 教室数」量级的无效教室试探 —— 这是实测中冲突检测次数下降的主要来源之一。

### 6.3 为什么用哈希键冲突矩阵

`ConflictMatrix` 把 `(教师/教室 id, 星期, 节次)` 打包成一个 `long long` 键存进 `std::unordered_set`：

```cpp
static long long pack(int id, const Slot& slot) {
    return (static_cast<long long>(id) << 20) | (slot.day_of_week << 10) | slot.period_no;
}
```

- 查询均摊 **O(1)**，且不产生节点分配（相比 `std::set` 的红黑树更省）；
- 与「每次尝试都遍历已排课表」的朴素做法（O(n)，n 为已排课次）相比，
  规模越大差距越明显（见第 8 节实测）。

### 6.4 教学班调度顺序 = 拓扑序

`run_placement(inputs, /*use_topology=*/true)` 时，教学班按「其课程在拓扑序中的位置」升序处理，
位置相同时按教学班编号。业务含义：**先修课先占资源**。
若改成按教学班编号顺序（`use_topology=false`，即朴素策略），资源紧张时被牺牲的可能恰是先修课 ——
`tests/test_scheduling.cpp::scheduling_topological_priority_protects_prerequisite_courses`
用 5 个时段 / 6 个课次需求的构造证明了这一点：拓扑序策略丢的是后继课程，朴素策略丢的是先修课。

## 7. 学生选课规则链

```
① 学籍状态 active                                     → EnrollmentClosedError
② 教学班存在 / 学期匹配 / 开放选课                      → EnrollmentClosedError / SchedulerError
③ 未重复选课                                          → SchedulerError
④ 教学班已完成排课(可由 REQUIRE_SCHEDULED_BEFORE_ENROLL 关闭) → NotScheduledError
⑤ 先修课程全部通过(分数 ≥ MIN_SCORE_TO_PASS)           → PrerequisiteError(列出缺哪几门)
⑥ 未超出学期学分上限(默认 25)                          → CreditLimitError
⑦ 教学班未满员                                        → CapacityError
⑧ 与本人本学期已选课程无时间冲突                        → TimeConflictError(列出冲突课程与时段)
通过 → 同一事务内: 写 enrollments + 刷新 teaching_classes.enrolled_count
```

- 判定逻辑全部落在 `rules.cpp` 的纯函数里（`missing_prerequisites` / `find_time_conflicts` /
  `exceeds_credit_limit`），**排课与选课共用同一套规则**，不会出现两处判定不一致。
- 退课为软删除（`status='dropped'`），保留历史便于审计与成绩追溯。
- 选课列表（`class_options`）会预先给出每门课的**不可选原因**，把失败提示前置到选课之前。

## 8. 效率基准测试

### 8.1 两种策略（同数据、同环境、只改算法）

| 对比项 | 策略 A · 本系统 | 策略 B · 朴素/人工式 |
| --- | --- | --- |
| 教学班顺序 | 拓扑序（先修优先） | 教学班编号顺序 |
| 冲突判定 | 哈希键集合，O(1) | 遍历已排课表线性扫描，O(n) |
| 教室候选 | 进入时段循环前算一次并排序 | 同样排序（保持公平） |
| 成败结果 | 硬约束相同 → 成功率一致，可横向对比 | 同 |

### 8.2 口径说明（避免"数字游戏"）

- 报告把耗时拆成 **数据装载 / 核心算法 / 落库** 三段（`load_us` / `algorithm_us` / `persist_us`）。
  演示数据只有 30 个教学班，读库+建图约 2~3 ms，**远大于**算法本身的几十微秒，
  因此结论一律以「核心算法耗时」为准，避免用"总耗时"掩盖真实差异。
- 基准运行前先做一次**预热**，避免首次建立数据库连接的开销污染第一个策略的均值。
- 每个策略重复 N 轮取平均；基准测试**不落库**（`persist=false`），不影响正式课表。
- 规模扫描使用放大的合成资源（充足容量的教室 + 7 天 × 8 时段）并放宽教师工作量上限，
  目的是让「冲突检测结构」成为唯一瓶颈，否则大规模时会先撞上资源上限。

### 8.3 实测数据（Ubuntu 24.04 / 8 vCPU / MySQL 8.0.36）

演示规模（30 个教学班 / 51 个课次）：

```bash
$ ./build/scheduler benchmark 20

│ 策略 A · 本系统      │       60 µs │      3 ms │          515 │ 100.0% │
│ 策略 B · 朴素/人工式 │       70 µs │      3 ms │        9,570 │ 100.0% │
  核心算法耗时下降: 14.3%    冲突检测次数下降: 94.6%    零失败轮次: 20/20
```

### 8.4 结论（含不利数据，避免夸大）

1. **冲突检测次数下降 94.6%（演示规模）／约 99%（180 班）** —— 这一项稳定且可复现。
2. **核心算法耗时**：30 班规模两策略接近（1.04×，线性扫描在极短数组上常数极小，甚至可能更快）；
   规模上来后优势放大，180 班约 **2 倍**。因此「效率提升 XX%」必须**连同规模一起说明**，
   单看小规模数据得出的百分比没有代表性。
3. **人工排课对比**：按「每个教学班 3 分钟」经验值估算（`.env` 的 `MANUAL_MINUTES_PER_CLASS` 可调），
   30 个教学班约 90 分钟人工工作量，而系统实测在毫秒级 —— 这是**量级差异的估算模型**，
   报告会原样打印参数，方便审阅者复核或替换为自家教务处的实测系数。
4. 首个版本曾出现"优化策略反而更慢"：教室候选被放在时段循环内层重复排序。
   修正为「循环外算一次」，并把教训写进代码注释（`scheduling_service.cpp`）与本文件。

## 9. 关键设计决策与取舍

| 决策 | 理由 | 代价 / 限制 |
| --- | --- | --- |
| 排课核心算法抽成**纯函数** `run_placement(快照)` | 可脱离数据库单测、可做纯算法基准、可预演 | 需维护一份内存快照结构 |
| `schedule_entries` 冗余 `teacher_id` / `course_id` | 让「教师时段唯一」「教室时段唯一」变成**数据库唯一索引**，硬保证不冲突 | 冗余字段与 teaching_classes 同步（同事务写入，无更新路径） |
| 排课以「周固定时段」为粒度（`week_start/week_end` 默认 1~16） | 与唯一索引直接对应，模型简单 | 暂不支持单双周交替上课 |
| 学生课表用**数据库视图** `v_student_timetable` | 多表 JOIN 固化在库侧，C++ 只做展示 | 视图变更需同步 schema 脚本 |
| 冲突检测用哈希键集合 | O(1)、无节点分配、实现简单 | 键打包依赖 id/节次取值范围（见 `pack()` 注释） |
| 口令用 `SHA2(学号#明文)` 在 **MySQL 侧**计算比对 | C++ 侧无需引入加密库，明文不进入业务层 | 演示用固定盐；生产应改 bcrypt/argon2 + 每人随机盐 |
| 演示口令统一 `123456` | 便于非技术用户快速体验 | 生产必须强制改密 |

## 10. 已知限制与后续优化

1. **当前目标是「可行解」而非「最优解」**：拓扑序 + 贪心 + 软约束排序。
   可扩展为把软约束（上午优先、教师集中排课、避免晚间）纳入代价函数，
   用局部搜索 / 模拟退火在可行解上迭代优化。
2. **未建模学生层面的班级冲突**：学分制下学生在选课时被拦截；
   若改为行政班统一排课，需在排课阶段加入「行政班-时段」约束。
3. **单双周 / 多时段课程**：当前一个课次对应一个"周固定时段"，扩展需放宽 `schedule_entries` 唯一索引。
4. **并发**：当前面向单线程 CLI；若 Web 化需为排课批次加乐观锁（`scheduling_runs` 已具备审计基础），
   并把 `Database` 换成连接池。
5. **测试策略**：单元测试全部使用内存数据（不依赖 MySQL），数据库相关的端到端流程
   通过 `run.sh demo` 与 CLI 子命令验收。
